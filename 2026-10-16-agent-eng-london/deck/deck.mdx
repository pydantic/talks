# What does that mean?

> Software development is a constrained, non-convex optimization problem.

<Row align="flex-start" gap="1.6rem">
<Col>

### Optimization

There are metrics and you want them better: speed, compatibility, memory, signups.

The agent is the optimizer. Stochastic, tireless, not picky about how.

</Col>
<Col>

### Constrained

Some things must stay true whatever the metric says: the spec, security, no `unsafe`.

Gates, not weights. The optimizer never gets to trade them.

</Col>
<Col>

### Non-convex

There is no single downhill path. Plenty of places "work" but aren't good, and the optimizer will stop in one.

Someone has to poke it.

</Col>
</Row>

<p style={{ marginTop: '1rem' }}>My job moved from finding **x** to choosing **f** and **g**. Review is one of the **g**'s.</p>

</Slide>

# Logfire Example

Our MCP server lets coding agents query Logfire directly with SQL and do (almost) **everything**. This lets our customers use Logfire as a metric or a constraint.

The constraints are obvious (security, isolation). The metrics are harder to define:

- Speed to achieve a goal (we can't measure token count)
- Valid SQL %

We get feedback by including an `intent` field in MCP tools.

# Where the metaphor breaks

- **Constraints are sampled, not proven.** CI checks points, not the region. Types and proofs are the exception, which is why the Dafny slide matters.
- **The optimizer can read the constraints.** A solver can't lobby you to relax a bound; an agent will edit the test. Fences need tamper-protection: branch protection, "never xfail", a human approval, credentials it doesn't have.
- **The real objective is a proxy.** Signups, revenue, "ease of use" aren't measurable until deployed. Goodhart's law applies to you, not just the model.

</Slide>
