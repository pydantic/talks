# What OpenTelemetry gives you

- **A wire format** - OTLP, plus semantic conventions for what to call things
- **Instrumentation for everything** - `opentelemetry-instrumentation-fastapi`, `-httpx`, `-asyncpg`, ~100 more
- **Any backend** - Jaeger, Tempo, Datadog, Logfire, a file

## What it doesn't give you

- **An opinion.** A tracer, a span and an attribute bag. The rest is up to you.
- Setting it up by hand is ~40 lines of provider, processor, exporter, resource
- And nothing in the spec says "show me this trace *while it runs*"

</Slide>

# Two lines

```py
import logfire
from fastapi import FastAPI

app = FastAPI()

logfire.configure()
logfire.instrument_fastapi(app)
```

- `instrument_fastapi` is `opentelemetry-instrumentation-fastapi` with our defaults, our message formatting, and our span tagging on top
- 34 `instrument_*` one-liners, all built the same way: Pydantic AI, OpenAI, Anthropic, httpx, asyncpg, Django, Celery, Redis, MCP, Monty, ...
- `logfire.configure()` reads `.logfire/`, env vars, or the token you pass - and works with no arguments

<Slide tab="opinions" space="tight">

# Opinion 1: the template is the name

```py
logfire.info('hello {name}', name=user)

# span name              'hello {name}'
# logfire.msg_template   'hello {name}'
# logfire.msg            "hello name=User(id=1, email='x@y.z', signed_up=datetime(...))"
# logfire.json_schema    {"properties": {"name": {"x-python-datatype": "PydanticModel", ...}}}
```

- The **template** is low cardinality: group, count, alert on it
- The **message** is rendered for humans, values included
- f-strings work too: `logfire.info(f'hello {user.email}')` - we recover the template from the AST with `executing`
- Attributes ride along as ordinary OTel attributes; the schema only carries what a JSON blob would lose

</Slide>

<Slide tab="opinions" space="tight">

# Opinion 2: values look like Python

<div style={{ display: 'grid', gridTemplateColumns: '1.1fr 1fr', gap: '1.5rem', alignItems: 'start' }}>

<div style={{ minWidth: 0 }}>

**What the wire carries**

```json
{"id": 1, "email": "x@y.z",
 "signed_up": "2026-01-01T09:30:00Z"}
```

plus, once per attribute, in `logfire.json_schema`:

```json
{"title": "User",
 "x-python-datatype": "PydanticModel",
 "properties": {"signed_up": {
   "type": "string", "format": "date-time",
   "x-python-datatype": "datetime"}}}
```

</div>

<div style={{ minWidth: 0 }}>

**What you see**

```py
User(
    id=1,
    email='x@y.z',
    signed_up=datetime(2026, 1, 1, 9, 30),
)
```

- `x-python-datatype` for models, dataclasses, `datetime`, `Decimal`, `UUID`, `Enum`, `Path`, exceptions
- DataFrames carry `x-columns`, `x-row-count`, `x-shape`
- Plain `str`, `int`, `float`, `bool` need nothing: `{}`

</div>

</div>

</Slide>

<Slide tab="opinions">

# Opinion 3: pending spans

- OTLP has no "span started" message. Exporters run on `on_end`, so a slow agent run is invisible until it finishes
- We emit a **zero-duration twin** when a span starts, tagged so the backend can reconcile it later

<PendingSpan />

- `RemovePendingSpansExporter` drops the twin when the real span lands in the same batch, so fast spans cost nothing
- Only the Logfire exporter sees them: your `additional_span_processors` never do

</Slide>

```ts
import * as logfire from 'logfire'

logfire.configure({ serviceName: 'weather-app' })

logfire.span('forecast for {city}', { city: 'Paris', units: 'C' }, {}, async () => {
```

# Hello, Rust

```rust
fn main() -> Result<(), Box<dyn std::error::Error>> {
    let logfire = logfire::configure().finish()?;
    let _guard = logfire.shutdown_guard();

    logfire::span!("forecast for {city}", city = "Paris").in_scope(|| {
        logfire::info!("got {days} days", days = 7u64);
    });
    Ok(())
}
```

- `cargo add logfire` - built on `tracing` and `opentelemetry`, so anything already instrumented with `tracing` just works
- Pending spans included; `logfire.msg` and `logfire.json_schema` are set by the macros
- It's the same crate the CLI is built on

# Demo: one trace, from agent to app

```py
logfire.configure(service_name='weather-app')
logfire.instrument_pydantic_ai()

app = FastAPI()
logfire.instrument_fastapi(app)

@app.get('/weather')

    return {'answer': result.output}
```

- HTTP request → Pydantic AI run → LLM call → Monty codemode execution → tool calls, one trace
- Pending spans: the trace is on screen before the model has answered

# Prompts are variables

```py
prompt = logfire.template_var(
    name='prompt__weather_agent',
    type=str,
    default='Combine tool calls into a single code execution call. Answer in {{units}}.',
    inputs_type=WeatherInputs,  # a BaseModel with `units: str`
)

with prompt.get(WeatherInputs(units='celsius'), label='production') as resolved:
    result = await weather_agent.run(question, instructions=resolved.value)
```

- A prompt is a managed variable named `prompt__<slug>`: versioned, targeted, rolled out like a feature flag
- Handlebars `{{placeholders}}`, and `@{other_variable}@` composition
- `logfire[variables]` extra in Python. Everyone else: Logfire speaks **OFREP**, so any **OpenFeature** client evaluates the same variables

</Slide>
