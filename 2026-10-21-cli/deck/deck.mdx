# What OpenTelemetry gives you

- **A wire format** - OTLP, plus semantic conventions for what to call things
- **Instrumentation for everything** - `opentelemetry-instrumentation-fastapi`, `-httpx`, `-asyncpg`, ~100 more
- **Any backend** - Jaeger, Tempo, Datadog, Logfire, a file

## What it doesn't give you

- **Defaults.** You assemble the provider, processor, exporter and resource yourself, ~40 lines before the first span
- **A span before it ends.** Exporters only receive finished spans, so a running request is invisible
- **Structure for values.** An attribute is a string, number, bool, or a flat list of those

</Slide>

# Two lines

```py
import logfire
from fastapi import FastAPI

app = FastAPI()

logfire.configure()
logfire.instrument_fastapi(app)
```

- `instrument_fastapi` calls `opentelemetry-instrumentation-fastapi`, then adds the message template and span-type attributes described next
- 34 `instrument_*` methods built the same way: Pydantic AI, OpenAI, Anthropic, httpx, asyncpg, Django, Celery, Redis, MCP, Monty, ...
- `logfire.configure()` reads the token from its argument, `LOGFIRE_TOKEN`, or `.logfire/`, in that order

<Slide tab="opinions" space="tight">

# Opinion 1: the template is the name

```py
logfire.info('hello {name}', name=user)

# span name              'hello {name}'
# logfire.msg_template   'hello {name}'
# logfire.msg            "hello name=User(id=1, email='x@y.z', signed_up=datetime(...))"
# logfire.json_schema    {"properties": {"name": {"x-python-datatype": "PydanticModel", ...}}}
```

- The **template** is the span name: low cardinality, so the UI can group, count and alert on it
- The **message** is the template with values substituted, for reading
- f-strings work too: `logfire.info(f'hello {user.email}')` - `executing` finds the call's AST and recovers the template
- Values are sent as ordinary OTel attributes; the schema records the Python types that JSON drops

</Slide>

<Slide tab="opinions" space="tight">

# Opinion 2: values look like Python

<div style={{ display: 'grid', gridTemplateColumns: '1.1fr 1fr', gap: '1.5rem', alignItems: 'start' }}>

<div style={{ minWidth: 0 }}>

**What the wire carries**

```json
{"id": 1, "email": "x@y.z",
 "signed_up": "2026-01-01T09:30:00Z"}
```

plus, once per attribute, in `logfire.json_schema`:

```json
{"title": "User",
 "x-python-datatype": "PydanticModel",
 "properties": {"signed_up": {
   "type": "string", "format": "date-time",
   "x-python-datatype": "datetime"}}}
```

</div>

<div style={{ minWidth: 0 }}>

**What you see**

```py
User(
    id=1,
    email='x@y.z',
    signed_up=datetime(2026, 1, 1, 9, 30),
)
```

- `x-python-datatype` for models, dataclasses, `datetime`, `Decimal`, `UUID`, `Enum`, `Path`, exceptions
- DataFrames carry `x-columns`, `x-row-count`, `x-shape`
- Plain `str`, `int`, `float`, `bool` need nothing: `{}`

</div>

</div>

</Slide>

<Slide tab="opinions">

# Opinion 3: pending spans

- OTLP has no "span started" message. Exporters run on `on_end`, so a 30-second agent run is invisible for 30 seconds
- When a span starts, the SDK exports a **zero-duration copy** of it, tagged so the backend can replace it later

<PendingSpan />

- `RemovePendingSpansExporter` drops the copy when the real span is in the same export batch, so short spans are sent once
- Only the Logfire exporter receives them; `additional_span_processors` do not

</Slide>

# Hello, TypeScript

```ts
import * as logfire from 'logfire'

logfire.configure({ serviceName: 'weather-app' })

logfire.span('forecast for {city}', { city: 'Paris', units: 'C' }, {}, async () => {
  const forecast = await fetchForecast('Paris')
  logfire.info('got {days} days', { days: forecast.length, forecast })
})
```

- `npm i logfire` - wraps `@opentelemetry/sdk-node` and Node auto-instrumentations
- `@pydantic/logfire-api` (zero deps, for libraries), `-browser`, `-cf-workers`
- Same `logfire.msg_template` / `logfire.msg` / `logfire.json_schema` attributes

# Hello, Rust

```rust
fn main() -> Result<(), Box<dyn std::error::Error>> {
    let logfire = logfire::configure().finish()?;
    let _guard = logfire.shutdown_guard();

    logfire::span!("forecast for {city}", city = "Paris").in_scope(|| {
        logfire::info!("got {days} days", days = 7u64);
    });
    Ok(())
}
```

- `cargo add logfire` - a `tracing` subscriber layer over `opentelemetry`, so existing `tracing` spans and events are exported unchanged
- Pending spans included; the macros set `logfire.msg` and `logfire.json_schema`
- The CLI is built on the same crate

# Demo: one trace, from agent to app

```py
logfire.configure(service_name='weather-app')
logfire.instrument_pydantic_ai()
logfire.instrument_monty()

app = FastAPI()
logfire.instrument_fastapi(app)

@app.get('/weather')
async def weather(q: str) -> dict[str, str]:
    result = await weather_agent.run(f"What's the weather in {q}, in Celsius?")
    return {'answer': result.output}
```

- One trace: HTTP request, Pydantic AI run, LLM call, Monty codemode execution, tool calls
- Pending spans: the trace is on screen before the model has answered

# Prompts are variables

```py
prompt = logfire.template_var(
    name='prompt__weather_agent',
    type=str,
    default='Combine tool calls into a single code execution call. Answer in {{units}}.',
    inputs_type=WeatherInputs,  # a BaseModel with `units: str`
)

with prompt.get(WeatherInputs(units='celsius'), label='production') as resolved:
    result = await weather_agent.run(question, instructions=resolved.value)
```

- A prompt is a managed variable named `prompt__<slug>`, with the same versions, targeting rules and rollouts as a feature flag
- Handlebars `{{placeholders}}`; `@{other_variable}@` inserts another variable
- Python uses the `logfire[variables]` extra. Other languages: Logfire serves **OFREP**, so any **OpenFeature** client can evaluate the same variables

</Slide>
